# Playbook: add a new internal app

Use this to add an app (e.g. "refunds dashboard") on the shared foundation. Read it end to end before starting. The KYC app in `src/apps/kyc/` is the reference implementation; copy its structure.

## 0. The rule that matters most

**Apps never touch the database or external systems directly.** All reads and writes go through `@/foundation/data`, and all external calls go through `getAdapters()` from `@/foundation/integrations`. That is what gives every app access control, masking and audit logging for free.

Inside `src/apps/<app>/` you must NOT import:
- `@prisma/client` (type-only model re-exports come from `@/foundation/data`)
- `@/foundation/db`
- `@/foundation/audit/writer` or `@/foundation/audit/query`
- `@/foundation/integrations/mocks/*`
- or call `fetch()`

`npm run lint` (ESLint `no-restricted-imports`) and `tests/architecture.test.ts` both fail if you do. Do not weaken either.

## 1. Inputs to collect (ask the user if missing)

| Input | Example (refunds) |
|---|---|
| App id (URL slug + audit `app` value) and display name | `refunds`, "Refunds dashboard" |
| Entity name and fields (type, required, which are **sensitive**) | `RefundRequest`: paymentId, customerEmail (sensitive), amountCents, currency, reason, status, requestedById, submittedById, decisionNote, providerRefundId |
| Statuses and transitions: for each transition, from → to, which roles, whether it is the "submit" step, whether it needs a checker (maker-checker) | `requested → pending_approval (submit)`, `pending_approval → approved/rejected (checker)`, `approved → refunded` |
| Role permissions per role: actions (`read`/`create`/`update`/`transition`), row scope, unmasked sensitive fields | analyst: create + read own; senior_reviewer: read all, approve; auditor: read |
| Integrations used and when | `PaymentsAdapter.refund()` when approved; Slack on approve/reject |
| Create flow: which roles create, form fields (required, ranges, options), and whether another system creates records via API | analyst + admin create from a "New refund" form; the support tool POSTs to `/api/refunds/request` |
| Screens | list with filters, detail with actions, new-record form, audit history |

Roles live in one place: `src/foundation/access/roles.ts`. Reuse the existing roles. Only add a role if the user asks for one; adding it there is the only foundation change allowed.

## 3. Data model

1. Add the Prisma model. Keep it Postgres-compatible: **no enums** (store statuses as `String`), JSON as `String`, `String @id @default(cuid())`, `createdAt`/`updatedAt`. Include `status String @default("<initial>")` and `submittedById String?` if there is an approval step. Add relations to `User` where useful (and the back-relations on `User`).
2. `npx prisma migrate dev --name <app>` to generate the migration (commit it).
3. Add `export type { <Model> } from "@prisma/client";` to `src/foundation/data/models.ts` and re-export it from `src/foundation/data/index.ts` (next to `KycCase`).
4. Add 15–25 realistic seed rows across all statuses to `prisma/seed.ts`. Clear the new table at the top of `main()` before `user.deleteMany()`. Seed some rows submitted by a senior reviewer so maker-checker can be demoed.

## 4. entity.ts

Copy `src/apps/kyc/entity.ts`. It contains:

```ts
export const APP_ID = "refunds";
export const REFUND_STATUSES = ["requested", "pending_approval", "approved", "rejected", "refunded"] as const;

export const refundWorkflow = defineWorkflow<RefundStatus>({
  statuses: REFUND_STATUSES,
  initial: "requested",
  transitions: {
    submit:  { label: "Submit for approval", from: ["requested"], to: "pending_approval", roles: ["analyst", "admin"], submits: true, variant: "primary" },
    approve: { label: "Approve", from: ["pending_approval"], to: "approved", roles: ["senior_reviewer", "admin"], requiresChecker: true, variant: "primary" },
    reject:  { label: "Reject",  from: ["pending_approval"], to: "rejected", roles: ["senior_reviewer", "admin"], requiresChecker: true, variant: "danger" },
  },
});

export const refundPolicy = definePolicy<RefundRequest>({
  roles: {
    analyst: { actions: ["read", "create", "update", "transition"], scope: { where: (u) => ({ requestedById: u.id }), matches: (u, r) => r.requestedById === u.id } },
    senior_reviewer: { actions: ["read", "update", "transition"], unmaskedFields: ["customerEmail"] },
    admin: { actions: ["read", "create", "update", "transition"], unmaskedFields: ["customerEmail"] },
    auditor: { actions: ["read"] },
  },
  sensitiveFields: { customerEmail: maskLast4 },  // or write your own Masker
});

export const RefundEntity = defineEntity<RefundRequest>({ app: APP_ID, type: "RefundRequest", model: "refundRequest", policy: refundPolicy, workflow: refundWorkflow });
```

Notes:
- `submits: true` records the actor in `submittedById`. `requiresChecker: true` blocks that same user (admins included).
- Roles missing from `policy.roles` get no access at all. `scope` is row-level security; `where` filters lists in the DB and `matches` guards single records. Provide both.
- `defineWorkflow` throws at startup if a transition names an unknown status.
- Every `sensitiveFields` entry is also **encrypted at rest** by the data helpers and stored only masked in audit snapshots. Consequences: declare sensitive fields as `String` in Prisma; don't filter or sort on them in `where`/`orderBy` (the DB holds ciphertext); fixtures that write with `db` directly must use `encryptField()` (see `makeCase` in `tests/helpers.ts`). Apps never import `@/foundation/crypto`.

## 5. service.ts, actions.ts, screens, manifest

### Foundation helpers (the only data API)

| Helper (`@/foundation/data`) | Use for | What it enforces |
|---|---|---|
| `listRecords(user, Entity, { where, orderBy, include, take })` | list pages | `read` permission, row scope merged into `where`, masking |
| `getRecord(user, Entity, id, { include })` | detail pages | `read` + row scope (throws `ForbiddenError`), masking |
| `getRecordHistory(user, Entity, id)` | per-record audit history | record read access, masking inside before/after |
| `createFromInput(user, Entity, fields, input, { action, build })` | **every create from a form or API** | `create` permission first, then `parseInput` validation against `fields`, then `build(values)` (map fields, call adapters; outside the transaction), then `createRecord` |
| `createRecord(user, Entity, data, { action })` | creates from trusted, already-built data (rare; prefer `createFromInput`) | `create` permission, initial status (status/submitter can't be set), encryption, **1 audit entry** |
| `updateRecord(user, Entity, id, data, { action, requireStatus, patch })` | field edits, notes, adapter results | `update` + scope, blocks status changes, **1 audit entry**. `patch(current)` receives the unmasked record (async allowed) for appends or adapter calls that need real values |
| `transitionRecord(user, Entity, id, transitionName, extraData)` | every status change | `transition` + scope, workflow validity, role, maker-checker, **1 audit entry** (`status_change:<name>`) |

Other foundation pieces:
- `can(user, action, { entity, record })` / `canSeeField(user, policy, field)` from `@/foundation/access`: for showing or hiding UI. The server-side checks happen inside the helpers anyway.
- `availableTransitions(user, workflow, record)` from `@/foundation/approvals`: returns the buttons to render, with `allowed=false` and a `reason` for maker-checker blocks (render them disabled).
- `getAdapters()` from `@/foundation/integrations`: `kycVendor`, `payments`, `notifications`. If you need a new external system: add an interface in `integrations/types.ts`, a mock in `integrations/mocks/`, wire it in `integrations/index.ts`, and add config to `integrations/config.ts` and `.env.example`. Never read `process.env` in an app.
- `getCurrentUser()` from `@/foundation/identity` (only in actions/screens; service functions take `user` as a parameter so they are testable). `listUsers({ role })` for pickers.
- `runAction(path, fn)`, `formString(fd, name)` and `formObject(fd)` from `@/foundation/actions`: wrap every server action so errors become a red banner and success a green one. Return `{ message, redirectTo }` to land on another page (e.g. the new record).
- `FieldSpec` / `parseInput` from `@/foundation/forms`: one field list drives the form UI and server-side validation (`required`, `min`/`max` for numbers, integer by default, `maxLength`, `options` for selects).
- `defineApi` from `@/foundation/api`: HTTP endpoints for other systems. See "Governed create flow" below.
- `ValidationError`, `ForbiddenError`, `TransitionError` from `@/foundation/errors`.
- UI from `@/foundation/ui`: `PageHeader`, `Banner`, `FilterBar`, `DataTable`, `DetailPanel`, `Form`, `CreateForm`, `ActionButtons`, `ApiButton`, `StatusBadge`, `AuditTrail`, `buttonClass`. Do not hand-roll tables or badges. Add a status color to `StatusBadge` `TONES` if it's a new status.

### service.ts
Pure functions `(user, ...) => Promise<...>` using only the helpers above. Put business rules here (e.g. "amount must be ≤ original payment", "notify Slack on approve/reject"). Call adapters after a successful `transitionRecord` (or inside `patch` if the result must be saved in the same audited update).

### Governed create flow (include by default)

Every app gets a create path that goes through the foundation, never direct DB writes. KYC is the reference (`src/apps/kyc/fields.ts`, `service.ts` `createCase`/`intakeSignup`, `screens/NewCase.tsx`, `api.ts`).

1. **Policy**: grant `create` only to the roles that should create (KYC: `senior_reviewer`, `admin`; not analysts).
2. **Fields** (`fields.ts`): a `FieldSpec[]`. Load dynamic options (e.g. assignees via `listUsers({ role })`) in the service so the server validates against the same list.
3. **Service**:
   ```ts
   export async function createRefund(user: Principal, input: Record<string, unknown>) {
     return createFromInput(user, RefundEntity, await refundFields(), input, {
       build: (v) => ({ paymentId: String(v.paymentId), amountCents: Number(v.amountCents), requestedById: user.id }),
     });
   }
   ```
   Never spread raw input into a record; `build` picks fields explicitly. Status is set by the foundation; the submitter is set by the foundation, or by `build` as `user.id` for create-as-submit.
4. **Action + screen**: `createRefundAction(_state: FormState, formData)` returns `runFormAction(formData, async (input) => { const r = await createRefund(user, input); return { message, redirectTo: appHref(APP_ID, r.id) }; })`. On a server-side error the form shows the message and keeps what the user typed (values come back in the action response, never the URL). `screens/New.tsx` calls `assertCan(user, "create", { entity })` and renders `<CreateForm fields={...} action={...} />`. Route `path[0] === "new"` to it in the manifest (before the detail route), and show a "New …" link (`buttonClass("primary")`) on the list page only if `can(user, "create", { entity })`.
5. **API intake (if another system creates records)**: add `api.ts` with `defineApi({ "<route>": { method: "POST", sessionPermission?, handler } })` and set `api` in the manifest. The foundation route `/api/<app>/<route>` authenticates the caller:
   - `Authorization: Bearer <token>` maps to a service account in `src/foundation/identity/service-accounts.ts` (role `integration`, token from `.env`; add the variable to `.env.example` and `scripts/ensure-env.mjs`). Grant that role only `create` in the policy.
   - Otherwise the user's session, same-origin only, plus `sessionPermission` if set (KYC uses `integrations:simulate`, admin only, for the demo button).
   - Handlers call the same `createFromInput` service function and return `{ status: 201, body }`. Errors map to 400/401/403/404/409.
   - For a demo trigger, render `<ApiButton endpoint={apiHref(APP_ID, "<route>")} body={sampleData()} label="Simulate …" />`. Apps never call `fetch` themselves.

### actions.ts
`"use server"`. Each action: read ids from FormData, `const user = await getCurrentUser()`, `return runAction(appHref(APP_ID, id), async () => { await service.x(user, ...); return "Message"; })`.

### screens
- `List.tsx`: `PageHeader`, `Banner`, `FilterBar` (status + one domain filter), `DataTable` with `rowHref` to the detail page.
- `Detail.tsx`: `DetailPanel` for fields (label masked fields "(masked for your role)"), an Actions panel driven by `availableTransitions` (use `Form` for transitions that need input), and an "Audit history" panel using `getRecordHistory` + `AuditTrail`. Auditors see "Read-only access."

### manifest.tsx + registry
```ts
export const refundsApp = defineApp({
  id: APP_ID, name: "Refunds dashboard", description: "…",
  canAccess: (user) => can(user, "read", { entity: RefundEntity }),
  render: async ({ user, path, searchParams }) =>
    path.length === 0 ? await List({ user, searchParams }) : await Detail({ user, id: path[0], searchParams }),
});
```
Then add it to the array in `src/apps/index.ts`. It appears in the nav and at `/apps/<id>`. Do not add files under `src/app/`; the catch-all routes serve every app's screens (`/apps/<id>/...`) and endpoints (`/api/<id>/<route>`).

## 6. Required tests (`tests/<app>.test.ts`)

Use `tests/helpers.ts` (seeded test users `ana`, `omar`, `sofia`, `raj`, `grace`, `maya`; add a `make<Entity>()` fixture). Fixtures may use `db` directly; assertions must go through the app's service. Cover:
1. **Row access**: a scoped role cannot `get`/`update` a record outside its scope (`ForbiddenError`), and its list excludes those records.
2. **Masking and encryption**: each sensitive field is masked for roles without permission and visible to roles with it; it is masked in `getRecordHistory` for every role; the raw DB row and raw `AuditLog` rows never contain the plaintext (see `tests/encryption.test.ts`).
3. **Maker-checker**: the user who performed the `submits` transition gets `MakerCheckerError` on each `requiresChecker` transition; a different checker succeeds.
4. **Invalid transitions**: wrong from-status, unknown transition and terminal statuses throw `TransitionError`; a role not granted a transition gets `ForbiddenError`; the status is unchanged afterwards.
5. **Audit**: every service mutation (create, each update kind, each transition) writes exactly one `AuditLog` row with correct `action`, actor, `before` and `after`; rejected mutations write none.
6. **Integrations**: adapter side effects happen when expected (e.g. a `Notification` row on approve/reject, payments refund called on approval).
7. Read-only roles (auditor) cannot mutate.
8. **Create** (see `tests/create.test.ts`): each role without `create` gets `ForbiddenError` from the service (even with invalid input) and nothing is written; a permitted create writes exactly one `AuditLog` row (`before: null`) and starts in the initial status; each validation rule (required, ranges, invalid options) throws `ValidationError` and writes nothing; status/submitter in the input are ignored. If there is an API: valid token → 201 with a service-account audit entry, bad token → 401, unpermitted session or cross-origin → 403, invalid body → 400 (call `handleApiRequest` with a `Request`).

## 7. Definition of done

- [ ] `npm install && npm run setup && npm run dev` works from a clean checkout (`npm run db:reset` re-seeds)
- [ ] `npm test`, `npm run lint`, `npm run typecheck` all pass
- [ ] Nothing in `src/apps/<app>` imports Prisma, the db client, audit internals, crypto or mocks; no `fetch`
- [ ] No foundation changes other than: model type re-export, a new adapter (if needed), StatusBadge tones. Anything else is flagged in the PR description
- [ ] App appears in the nav for roles with `read`, and is hidden for others
- [ ] Governed create flow: `New` form for the roles with `create` (hidden and refused for others), validated by the shared `fields`; API endpoint if another system creates records
- [ ] Verified in the browser as one user per role: list scope, masking, buttons by role and status, maker-checker disabled button, create form (and validation error), audit history updates after each action, global Audit log shows the entries with `app=<id>`
- [ ] README "Apps" list updated; small logical commits; PR summary lists any shortcuts
